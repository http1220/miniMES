# 알람 큐 거부 정책 학습 기록

- 날짜: 2026-10-11 (KST)
- 요구사항: DET-08, D-084
- 구현: `../../src/Core/RejectingAlarmQueue.cs`
- 테스트: `RejectingAlarmQueueTests.cs`

## 1. 목표와 범위

용량이 제한된 큐에 알람을 순서대로 보관한다.
꽉 차면 기존 항목을 보존하고 새 항목만 거부한다. 거부할 때마다 RejectedCount를 증가시킨다.
오류 로그, 전송 후 삭제, 취소 규칙의 연결은 이번 범위에서 제외했다.

| 용량 3에서 1, 2, 3, 4 추가 | 남은 항목 | 누적 개수 |
|---|---|---|
| 기존 샘플 버퍼 | [2, 3, 4] | DroppedCount = 1 |
| 이번 알람 큐 | [1, 2, 3] | RejectedCount = 1 |

## 2. 처음 작성한 형태

RejectingAlarmQueue<T>에 용량 필드, 빈 Queue<T>, public get·private set의 long RejectedCount를 작성했다.
제네릭으로 항목 자료형을 사용할 때 지정하고, 테스트에서는 int를 사용했다.
생성자는 용량 0 이하를 ArgumentOutOfRangeException으로 거부하도록 작성했다.
처음에는 필드 저장 후 검사했지만, 검증 후 저장하면 흐름이 명확하다는 피드백을 받았다.
현재 파일은 검사 후 필드에 저장한다.

Add는 빈 메서드로 시작했고 GetSnapshot은 Queue.ToArray 결과를 반환하도록 만들었다.
조회는 항목을 삭제하지 않고 오래된 순서의 별도 배열을 반환한다.

## 3. 실패 확인과 개선 과정

1. 용량 이내에 1, 2, 3을 추가하는 테스트를 먼저 작성했다.
2. Add가 비어 있어 실제 결과가 빈 배열이므로 실패했다.
3. Enqueue로 추가하는 최소 구현을 넣어 통과시켰다.
4. 네 번째 항목 4를 거부하는 테스트를 추가했다.
5. 모든 항목을 넣던 구현이 [1, 2, 3, 4]를 반환하여 실패했다.
6. Add에서 개수가 용량 이상이면 RejectedCount를 증가시키고 즉시 반환하도록 수정했다.
7. 여유가 있을 때만 Enqueue를 실행하게 하여 기존 항목을 보존했다.

핵심은 가득 찬 분기에서 Dequeue를 호출하지 않는 것이다.
샘플 버퍼와 구조가 비슷해도 넘쳤을 때의 업무 정책은 반대다.
이름은 expected_items보다 expectedItems가 일반적인 C# 변수 표기에 맞는다는 피드백도 받았다.

## 4. 검증한 사례

| 입력 또는 조건 | 기대 결과 |
|---|---|
| 용량 3, 1·2·3 추가 | [1, 2, 3], 거부 0 |
| 용량 3, 1·2·3·4 추가 | [1, 2, 3], 거부 1 |
| 용량 3, 1·2·3·4·5 추가 | [1, 2, 3], 거부 2 |
| 용량 0 또는 -1 | 생성자에서 ArgumentOutOfRangeException |

Fact 세 개와 Theory 두 사례로 총 5개 실행 사례다.
사용자가 단계별 테스트 통과를 확인했다. 문서 작성 시 테스트를 별도로 실행하지 않았다.

## 5. 남은 작업

거부 사실을 오류 로그로 남기는 연결, 전송 처리, 미전송 발생과 해제의 취소 연결은 별도 작업이다.
현재 Add는 반환값이 없고 거부 누적 개수만 제공한다.
수집기에서 특정 발생의 거부 여부를 알아내어 추적기에 기록하는 연결 방식은 아직 구현하지 않았다.
