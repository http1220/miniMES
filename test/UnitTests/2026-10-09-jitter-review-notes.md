# 지터 계산 구현과 리뷰·개선 기록

- 날짜: 2026-10-09 (KST)
- 규칙: D-093, 기본 대기시간에 0~+20%를 더하며 감소시키지 않는다.
- 설계 전제: Core는 난수를 생성하지 않는다. Collector가 생성한 0~1의 비율을 인자로 전달한다.
- 계산: 기본 대기시간 × (1 + 0.2 × 비율)
- 검증 결과: 사용자가 최종 변경 후 테스트 통과를 확인했다. 문서 작성 시 테스트를 다시 실행하지는 않았다.

## 1. 처음 작성한 구현과 테스트

처음에는 ConnectionBackoff 클래스 안에 static ApplyJitter 메서드를 추가했다.
기본 대기시간과 비율을 인자로 받고 TimeSpan.FromSeconds로 결과를 반환했다.
계산에는 baseDelay.Seconds를 사용했다.

첫 테스트 ApplyJitter_threetimes에서는 ConnectionBackoff 객체를 만들고 첫 실패로 기본 대기시간 1초를 얻었다.
그 시간을 세 번의 지터 계산에 사용했다.

| 기본 대기시간 | 비율 | 처음 작성한 기대 결과 |
|---|---:|---|
| 1초 | 0 | 1초 |
| 1초 | 1 | 1.2초 |
| 1초 | 0.5 | 1.1초 |

이 테스트들은 통과했다. 난수를 인자로 받는 방향과 비율 계산식은 올바르게 작성되어 있었다.
하지만 기본 입력이 모두 1초여서 시간 변환의 오류는 드러나지 않았다.

## 2. 리뷰에서 지적한 내용

### 전체 시간 대신 초 구성 요소를 사용한 오류

Seconds는 전체 시간을 초로 환산하지 않는다. TimeSpan의 초 구성 요소만 정수로 반환한다.
따라서 소수 부분과 분·시간 부분이 계산에서 빠진다.

| 원래 시간 | Seconds | TotalSeconds |
|---|---:|---:|
| 1초 | 1 | 1 |
| 1.5초 | 1 | 1.5 |
| 60초 | 0 | 60 |
| 1분 15초 | 15 | 75 |

기본 시간이 1.5초이고 비율이 0이라면 원래 시간을 유지해야 한다.
하지만 초기 구현은 1초를 반환한다. 60초 입력에서는 0초를 반환할 수도 있다.
처음 테스트의 1초에서는 두 속성의 값이 같아서 테스트가 통과했다.

### 감소하지 않는다는 조건의 검증 부족

처음 테스트는 비율 0, 0.5, 1에서 정확한 계산 결과를 확인했다.
여러 비율에서 결과가 기본 시간 이상이며 +20% 이내인지 확인하는 범위 테스트는 없었다.

### 기본 백오프와 지터의 역할 분리

요청은 ConnectionBackoff와 별개의 순수 계산 함수였다.
처음 구현은 순수 함수였지만 ConnectionBackoff 안에 있었다.
또한 지터 테스트가 기본 시간을 얻기 위해 백오프 객체를 호출해서 두 기능의 준비 과정이 묶여 있었다.

## 3. 개선 과정

### 시간 계산을 TotalSeconds로 변경

Seconds를 TotalSeconds로 변경했다.
전체 대기시간을 double형 초 수로 얻어 비율을 곱한 뒤 TimeSpan으로 변환하도록 수정했다.
이를 통해 분 단위와 소수 초가 계산에서 사라지는 문제를 해결했다.

### 범위 테스트를 작성하면서 확인 방식 수정

처음 추가한 Theory는 비율 0, 0.25, 0.5, 0.75, 1을 전달했지만,
각 결과가 모두 정확히 1초라고 Assert.Equal로 확인했다.
이는 더하기 지터의 규칙과 달랐다. 예를 들어 1초에 비율 0.5면 1.1초여야 한다.

개선한 테스트에서는 백오프 호출 없이 기본 대기시간 10초를 직접 준비했다.
ApplyJitter 반환값을 actualDelay에 저장하고 Assert.InRange로 10초 이상 12초 이하인지 확인했다.
테스트 이름은 ApplyJitter_ValidFraction_ReturnsWithinAllowedRange로 변경했다.

| 항목 | 초기 범위 테스트 | 개선한 범위 테스트 |
|---|---|---|
| 기본 시간 준비 | 백오프 첫 실패로 1초 획득 | TimeSpan으로 10초 직접 준비 |
| 확인 방식 | 모든 비율에서 1초와 같음 | 모든 제시 비율에서 10~12초 범위 |
| 확인 목적 | 지터 계산 규칙과 불일치 | 감소 없음과 최대 증가율 확인 |

범위 검사만 있으면 항상 기본 시간을 반환하는 잘못된 구현도 통과할 수 있다.
따라서 비율 0, 0.5, 1의 정확한 결과를 확인하는 기존 테스트도 유지했다.
다섯 비율을 검사한 것이 모든 실수 입력을 전수 검사한 것은 아니다.

### 소수 시간 유지 테스트 추가

ApplyJitter_ZeroFraction_PreservesFractionalDelay를 추가했다.
기본 시간 1.5초, 비율 0의 결과가 정확히 1.5초인지 확인한다.
이 테스트는 나중에 Seconds를 다시 사용하면 실패하므로 수정한 오류의 재발을 막는다.
사용자는 추가 후 테스트 통과를 확인했다.

### 별도 DelayJitter 클래스로 이동

Core에 DelayJitter 클래스를 만들고 static ApplyJitter를 옮겼다.
현재 함수는 baseDelay.TotalSeconds와 전달받은 randomFraction만 사용한다.
지터 테스트의 호출 대상도 DelayJitter.ApplyJitter로 변경했다.

ConnectionBackoff는 실패 이력에 따른 기본 대기시간을 계산하고,
DelayJitter는 그 시간에 전달받은 비율을 적용한다.
기본 백오프의 상한은 10초지만 지터를 더한 최종 시간은 최대 12초가 될 수 있다.

## 4. 현재 파일에서 확인한 상태

| 역할 | 파일 |
|---|---|
| 지터 계산 | `../../src/Core/DelayJitter.cs` |
| 기본 백오프 | `../../src/Core/ConnectionBackoff.cs` |
| 백오프·지터 테스트 | `ConnectionBackoffTests.cs` |

문서 작성 시 확인한 지터 테스트는 다음과 같다.

| 테스트 | 실행 사례 수 | 확인 내용 |
|---|---:|---|
| ApplyJitter_threetimes | 1 | 1초에 비율 0, 1, 0.5를 적용한 정확한 결과 |
| ApplyJitter_ValidFraction_ReturnsWithinAllowedRange | 5 | 10초에 다섯 비율을 적용한 결과가 10~12초인지 |
| ApplyJitter_ZeroFraction_PreservesFractionalDelay | 1 | 1.5초에 비율 0 적용 시 소수 부분 유지 |

지터 테스트는 현재 ConnectionBackoffTests 안에 남아 있다.
별도 DelayJitterTests.cs로 옮기는 것은 제안했지만, 문서 작성 시 해당 파일은 없었다.
정확한 결과 비교 테스트도 아직 백오프 객체로 기본 1초를 준비하고 있다.
이 부분은 함수 계산의 오류는 아니며, 테스트 역할 분리를 위해 추가 정리할 수 있다.

## 5. 이번 작업에서 배운 점

- 테스트가 통과해도 선택한 입력이 오류를 드러내지 못할 수 있다.
- 시간 전체를 계산할 때는 구성 요소와 전체 단위 환산 속성을 구분해야 한다.
- 정확한 값 비교와 허용 범위 검사는 서로 다른 종류의 오류를 잡는다.
- 기본 입력을 직접 준비하면 순수 함수의 테스트가 다른 기능에 의존하지 않는다.
- 무작위 비율을 외부에서 전달받으면 테스트에서 원하는 비율을 고정할 수 있다.
- 함수는 실제 기다림이나 난수 생성을 하지 않고 적용 결과만 계산한다.

## 6. 현재 전제와 남은 정리

randomFraction은 0~1이고 baseDelay는 정상적인 비음수 대기시간이라는 전제로 구현했다.
범위 밖 비율, NaN, 무한대, 음수 시간, TimeSpan 표현 범위를 넘는 입력을 어떻게 처리할지는 이번에 정하지 않았다.
기본 백오프가 사용하는 1~10초 범위의 계산을 검증했으며 임의의 tick 단위 정밀도 보장까지 검증한 것은 아니다.

추가 정리 후보는 지터 테스트의 별도 클래스 이동, 첫 지터 테스트의 기본 시간 직접 준비,
그리고 테스트 이름 ApplyJitter_threetimes를 검사 목적이 드러나는 이름으로 변경하는 것이다.
이번 문서 작성에서는 소스 코드와 테스트를 수정하지 않았다.
