## 1. 샘플의 최종 결과 만들기

입력은 원본 측정값(float), 유효 범위(min, max), 원본 상태 코드(ushort)다.
ValidateSample은 측정값과 상태를 독립적으로 판정하고 SampleValidationResult 하나를 반환한다.

| 측정값 | 상태 코드 | 최종 측정값 | 최종 상태 코드 | IsInvalid |
|---|---|---|---|---|
| 유효 | 유효 | 원래 값 | 원래 코드 | false |
| 무효 | 유효 | null | 원래 코드 | true |
| 유효 | 무효 | 원래 값 | null | true |
| 무효 | 무효 | null | null | true |

경계값은 연습에서 정한 포함 규칙에 따라 유지한다.
이 결과는 저장할 데이터의 형태를 만드는 것이며 실제 DB 저장을 수행하지 않는다.

## 2. nullable과 조건 연산자

- float?와 ushort?는 원래 자료형의 값 또는 null을 담을 수 있다.
- null은 값 없음이며, 0이나 NaN과 다르다.
- HasValue는 해당 nullable 변수에 값이 있는지만 확인한다. 유효 범위를 검사하지 않는다.
- Value는 실제 값을 읽는다. null인 상태에서 읽으면 예외가 발생한다.
- 원본 250을 그대로 nullable 변수에 넣으면 HasValue는 true다.
- 유효 범위 0~200으로 ValidateSample을 거친 250은 null로 바뀌므로 결과의 HasValue는 false다.
- 조건 연산자에서 ?는 참일 때의 선택, :는 거짓일 때의 선택을 구분한다.
- 자료형 뒤의 ?는 nullable을 뜻하며 조건 연산자의 ?와 역할이 다르다.
- C# 7.3에서는 값과 null을 선택하는 조건식의 자료형을 맞추기 위해 nullable 변환을 사용했다.

## 3. 결과 타입과 리팩터링

처음에는 public 필드 세 개로 결과를 표현했다.
이후 외부에서 결과를 바꾸지 못하도록 get만 있는 자동 프로퍼티로 변경했다.
생성자에서 측정값과 상태 코드 두 값을 받아 보관한다.
IsInvalid는 두 값 중 하나라도 null인지 결과 클래스가 직접 계산한다.
이를 통해 값은 비어 있는데 이상값 표시만 false로 전달되는 모순을 막았다.

ValidateSample에서는 측정값과 상태의 유효성을 각각 한 번 계산하고 지역 변수로 재사용한다.
검사 결과를 재사용하는 목적은 작은 성능 차이보다 판정 근거를 일관되게 표현하는 데 있다.
기존 테스트를 유지하면서 내부 구조만 개선하는 작업이 리팩터링이다.

## 4. 상태와 이벤트 구분

ThresholdAlarmDetector는 연속 초과 횟수, 연속 정상 횟수, 현재 알람 발생 여부를 기억한다.
따라서 같은 입력열은 같은 객체에 순서대로 전달해야 한다.
각 객체의 상태는 독립적이며 설비별 감지 객체가 서로의 횟수를 공유하면 안 된다.

AlarmEvent 열거형은 이번 호출에서 일어난 변화를 표현한다.
선택지는 None, Raised, Cleared이며 C#의 일반적인 이름 관례인 PascalCase를 사용했다.

| 상황 | 이번 이벤트 | 처리 후 상태 |
|---|---|---|
| 미발생 상태에서 세 번째 연속 초과 | Raised | 발생 중 |
| 이미 발생 중이며 초과가 계속됨 | None | 발생 중 |
| 발생 중에 첫 번째 또는 두 번째 정상 | None | 발생 중 |
| 발생 중에 세 번째 연속 정상 | Cleared | 미발생 |
| 해제 후 정상이 계속됨 | None | 미발생 |

이벤트 없음은 알람이 없다는 뜻이 아니다. 이번 호출에 상태 변화가 없다는 뜻이다.

## 5. 임계 초과 판정 규칙

- 값이 상한보다 클 때만 초과다. 상한과 같으면 정상이다.
- 연속 초과 3회에 알람을 발생시키고 이미 발생 중이면 발생 이벤트를 반복하지 않는다.
- 연속 정상 3회에 해제하고 미발생 상태에서는 해제 이벤트를 내지 않는다.
- 초과 입력은 정상 횟수를 0으로 초기화한다.
- 정상 입력은 초과 횟수를 0으로 초기화한다.
- 횟수는 3까지만 증가한다. 필요한 정보는 3회 도달 여부이기 때문이다.

증가 전 값을 반환하는 후위 ++를 같은 변수의 대입식에 사용하면 증가 결과가 덮어써질 수 있음을 배웠다.
카운터 제한에는 현재 값에 1을 더한 결과를 선택해 대입하는 방식을 사용했다.

## 6. 무효 측정값 건너뛰기 정책

이번 학습에서 사용자가 선택한 정책은 무효 측정값을 건너뛰고 이전 횟수와 알람 상태를 유지하는 것이다.
이 정책에서 연속은 유효한 측정값들의 입력 순서를 기준으로 한다.
이 선택을 요구사항에 확정된 규칙으로 혼동하지 않고, 프로젝트 결정 기록에 반영할 사항으로 구분한다.

NaN은 대소 비교가 false이므로 별도 검사 없이 정상 분기로 들어갈 수 있다.
NaN은 ==로도 판별할 수 없으며 전용 IsNaN 검사를 사용한다.
양·음의 무한대도 별도로 검사하여 이벤트 없음으로 즉시 반환한다.
무효 값은 초과나 정상으로 세지 않으며 이전 카운터도 초기화하지 않는다.

유한한 숫자의 유효 범위 밖 여부는 Update의 상한만으로 판단할 수 없다.
먼저 ValidateSample로 유효성을 판정하고 결과의 측정값이 없는 경우 연결 단계에서 건너뛴다.

## 7. 실제 연결 메서드

SampleAlarmProcessor.Process는 판정 결과, 기존 감지 객체, 알람 상한을 받는다.

1. 결과의 Measurement가 없으면 None을 반환한다. 감지 객체를 호출하지 않는다.
2. 값이 있으면 그 측정값으로 detector.Update를 호출하고 이벤트를 반환한다.

Measurement.HasValue가 false인지 확인하는 것은 Measurement가 null인지 확인하는 것과 같은 동작이다.
샘플 전체의 IsInvalid로 건너뛰면 상태 코드만 무효인 경우에도 유효 측정값을 버리므로 의도에 맞지 않는다.

| 판정 결과 | 측정값 알람 처리 | 상태 기반 가동 판단 |
|---|---|---|
| 측정값 유효, 상태 무효 | 측정값으로 계속 판단 | 상태를 알 수 없어 공백 |
| 측정값 무효, 상태 유효 | 건너뛰고 횟수 유지 | 유효 상태로 판단 가능 |

가동 판단의 공백 처리 자체는 이번 연결 메서드에서 구현한 기능이 아니다.
Process는 자체 상태가 없어 static으로 만들 수 있지만, 전달받은 감지 객체의 상태를 변경하므로 순수 함수는 아니다.

## 8. 테스트 작성에서 배운 점

- 테스트 먼저 작성하고 실패를 확인한 다음 최소 구현으로 통과시켰다.
- 컴파일 오류는 테스트 실패와 다르다. 실행 가능한 선언과 임시 반환이 있어야 기대 결과 비교가 가능하다.
- 정상 흐름만 통과하는 임시 구현에 초과·무효 사례를 추가하여 누락된 동작을 확인했다.
- 발생 중 회복을 검사하려면 같은 객체에서 알람을 먼저 발생시켜야 한다.
- 상태가 있는 Update를 Assert 안에서 다시 호출하면 입력이 한 번 더 처리된다.
- 각 샘플은 의도한 횟수만큼 호출하고 반환값을 확인해야 한다.
- 기대 목록을 만들기만 해서는 검사가 되지 않는다. 실제 목록과 Assert.Equal로 비교해야 한다.
- ForEach로 Process를 호출하기만 하면 반환 이벤트가 버려진다. List<AlarmEvent>에 결과를 모았다.
- 목록 비교는 길이와 각 위치의 이벤트를 확인한다. 실패의 pos 3은 네 번째 위치다.
- 테스트 안에 있던 HasValue 분기를 실제 Core의 Process로 옮기고 테스트가 그 메서드를 호출하도록 바꿨다.
- 상태 코드만 무효인 테스트도 Process를 거치게 하여 잘못된 IsInvalid 조건을 잡아낼 수 있게 했다.
- 파일을 모두 저장한 뒤 테스트해야 현재 편집한 내용이 빌드에 반영된다.

## 9. 검증한 입력열

| 사례 | 기대 동작 |
|---|---|
| 정상 3회 | 모두 None |
| 초과 3회 | 처음 두 번 None, 세 번째 Raised |
| 초과 5회 | 세 번째에만 Raised |
| 발생 중 정상 3회 | 세 번째 Cleared |
| 발생 중 정상 2회 후 초과 | 정상 횟수 초기화, 다시 정상 3회에 해제 |
| 초과 2회 후 상한과 같은 값 | 초과 횟수 초기화 |
| 발생 중 정상 5회 | 세 번째에만 Cleared |
| 발생, 해제, 다시 초과 3회 | 재발생 가능 |
| 두 객체의 호출을 섞음 | 각각 자기 세 번째 초과에 발생 |
| 회복 중 NaN | 건너뛰고 정상 횟수 유지 |
| 초과 도중 NaN·무한대 | 건너뛰고 초과 횟수 유지 |
| 측정값 유효, 상태 코드 무효 | Process를 통해 세 번째에 발생 |
| 150, 160, 범위 밖 250, 170 | 무효 샘플을 건너뛰고 마지막에 발생 |

샘플 판정에는 정상, 측정값만 무효, 상태만 무효, 둘 다 무효, 양쪽 경계값의 6개 실행 사례를 추가했다.
이전 기본 판정 14개와 합쳐 20개가 되었고, 이후 알람·연결 사례를 추가해 35개 전체 통과를 확인했다.
오늘 사용자가 연결 테스트 변경 후 전체 테스트 통과를 다시 확인했다.
이 문서 작성 시 테스트를 별도로 재실행하지는 않았다.
