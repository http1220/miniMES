# 0015. 수집기 동시성: 역할별 비동기 루프

- 상태: 채택
- 날짜: 2026-10-03
- 관련: ADR 0002(플랫폼), ADR 0005(시각), ADR 0006(저장 실패 처리)

## 맥락

수집기는 설비마다 독립적으로 폴링하고, 한 설비의 지연·끊김이 다른 설비나 저장·생존 신호를 막지 않아야 한다. 이 프로젝트의 설비는 5대지만, 공개 자료를 보면 공장 단위 수집기 1대가 맡는 설비는 수십~100대 수준도 흔하다(업체 사례 기준, 참고 수준). 설비 수만큼 스레드를 늘리는 구조는 이 범위를 넘어가면 부담이 커진다.

.NET Framework 4.8에는 `PeriodicTimer`와 Channels가 없고, `NetworkStream`의 비동기 읽기는 이미 진행 중이면 취소 토큰을 따르지 않는다(.NET Core 이후에는 취소 가능).

## 결정

- **역할별 비동기 루프**: 설비 루프(설비당 1개) · 판정 루프(1초, 통신 이상) · 전송 루프 · 생존 신호 루프(2초). 전송이 타임아웃에 걸려도 판정과 생존 신호는 멈추지 않는다
- **응답 타임아웃이 나면 그 연결을 닫는다**. 진행 중인 읽기가 예외로 끝나고, 늦게 온 응답이 다음 요청과 섞일 가능성이 사라진다. 다음 주기에 백오프 없이 다시 연결한다(백오프는 연결 실패에만)
- **수집 시각은 유효 응답을 받은 순간**이다. 장비가 값을 읽은 정확한 순간은 폴링 방식으로 알 수 없으므로 상용 드라이버의 관행을 따랐다. 오차 상한은 왕복 시간(최대 요청 타임아웃)이다
- **버퍼·큐 정책은 스레드와 무관한 순수 객체**로 만들어 단위 테스트로 검증하고, 수집기에서 lock 하나로 감싼다. lock 안에서는 await하지 않는다. 전송한 항목은 응답 후 **키로 지운다**. 그래서 전송 중 버퍼가 넘쳐 앞쪽 항목이 버려져도 엉뚱한 항목을 지우지 않는다
- **예상한 실패**(타임아웃, 끊김, 장비 예외 응답, HTTP 오류)는 루프 안에서 분류해 처리한다. **분류 밖 예외로 루프가 끝나면 프로세스를 종료**한다. 생존 신호가 끊겨 화면에 "수집기 정지"가 뜨고, 버그가 장비 통신 이상으로 위장되지 않는다
- 같은 호스트로의 동시 HTTP 연결 수 기본 제한을 설정으로 올려, 생존 신호가 전송 요청 뒤에 줄 서지 않게 한다

## 검토한 대안

- **설비당 전용 스레드 + 동기 소켓 타임아웃**: 단순하고 격리가 구조로 보이지만, 스레드 수가 설비 수에 묶인다
- **스레드 풀 타이머 콜백**: 응답이 주기보다 늦으면 콜백이 겹쳐 재진입 방지가 필요하다
- **연결 유지 + 트랜잭션 ID 대기표(수신 루프 분리)**: 요청을 여러 개 동시에 보낼 수 있지만 실패 경로가 늘고, 한 번에 하나만 처리하는 장비나 게이트웨이 앞에서는 이득이 작다
- **ConcurrentQueue / BlockingCollection / TPL Dataflow**: "오래된 것부터 버림 + 응답 후 삭제" 정책을 표현하기 어렵거나, 가득 찼을 때 생산자를 막는다
- **한 주기 안에서 판정·전송·생존 신호를 차례로 실행**: 전송 타임아웃 동안 나머지가 함께 멈춘다
- **모든 예외를 잡고 계속 / 죽은 루프만 재시작**: 버그가 무한 반복되거나, 손상됐을 수 있는 공유 상태 위에서 다시 돈다

## 결과와 한계

- 설비 간 1초 미만의 사건 순서는 보장하지 않는다. 정밀한 순서가 필요하면 장비 측 타임스탬프(DNP3, IEC 61850, 사건 순서 기록)가 필요하며 범위 밖이다
- RS-485 멀티드롭(Modbus RTU)은 범위 밖이다. 한 라인에서 한 번에 한 트랜잭션만 진행되므로, 도입한다면 격리 단위는 설비가 아니라 **라인(연결)**이 되고 라인당 루프 하나를 둔다
- 지연 설비는 매 주기 다시 연결한다. 5대 규모에서의 영향은 테스트 단계에서 관찰한다
