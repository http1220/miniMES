# 0006. 저장 실패 처리: 수집기 버퍼, 끝까지 확인, 알람 큐 분리

- 상태: 채택
- 날짜: 2026-09-30

## 맥락

Server나 DB가 끊겨도 수집은 멈추지 않아야 하고, 무엇을 잃었는지 설명할 수 있어야 한다.

## 결정

- **버퍼는 수집기 한 곳**(메모리)에만 둔다. 한도는 기본 설정에서 10분 분량(약 3,000건, 5대 × 600초 계산값)
- Server는 버퍼 없이 중계하고, **DB 커밋이 끝난 뒤에만** "저장됨"을 응답한다. 수집기는 응답받은 샘플만 버퍼에서 지운다
- 재전송으로 생기는 중복은 키(설비 + 실행 ID + 순번)로 막는다
- 샘플 버퍼가 가득 차면 **가장 오래된 샘플부터 버리고** 버린 건수를 기록한다
- 알람 이벤트는 **샘플과 다른 큐**에 두고, 복구되면 먼저 보낸다. 가득 차면(기본 3,000건) **새 이벤트를 거부**하고 오류 로그와 건수를 남긴다
- 버퍼에 시간 한도는 두지 않는다

## 검토한 대안

| 대안 | 버린 이유 |
|---|---|
| 수집기 + Server 양쪽 버퍼 | 유실 지점·한도가 두 곳이 되고 Server 재시작 시 유실 |
| Server에만 버퍼 | 수집기↔Server 단절 시 즉시 유실 |
| 알람을 샘플과 같은 버퍼에 | 넘칠 때 알람 "발생"이 버려지고 "해제"만 남을 수 있다 |
| 시간 한도 추가 | 샘플은 이력이라 늦게라도 원래 시각으로 저장하는 게 유효하다. 고정 주기라 건수 한도가 시간 한도 역할을 한다 |

참고: Rapid SCADA 6의 Communicator도 현재값 큐는 오래된 것부터 버리고, 이벤트 큐는 새 항목을 거부한다(공개 소스 확인).

## 결과

- 수집기 재시작 시 버퍼에 있던 데이터는 잃는다(허용 범위로 정의)
- **디스크 임시 저장은 개선안**이다. 수집기 재시작에도 데이터를 보존할 수 있지만, 파일 손상·용량 관리라는 새 실패 경로가 생긴다
