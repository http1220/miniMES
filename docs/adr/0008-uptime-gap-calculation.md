# 0008. 가동·공백 구간을 저장하지 않고 계산

- 상태: 채택
- 날짜: 2026-09-30

## 맥락

MTBF는 가동 시간 합계에서 수집 공백을 뺀 값이 필요하다. 샘플은 재전송(ADR 0006) 때문에 순서 없이 늦게 도착할 수 있다.

## 결정

- 가동·공백 구간을 **저장하지 않고 조회 시 원본 샘플에서 계산**한다
- 계산은 **Core(C#)**에서 한다. DB에서는 설비·기간의 샘플을 시각 순으로 읽기만 한다. 판정 규칙이 한 곳에 있고, CI 단위 테스트로 검증할 수 있다
- 설비별 연속 두 샘플의 간격 Δ로 판정한다
  - Δ ≤ T(통신 이상 판정 시간, 기본 5초): 앞 샘플의 상태로 계산
  - Δ > T: 구간 전체가 수집 공백(시작 = 마지막 성공 샘플)
  - 상태 코드가 무효인 샘플에서 시작하는 구간은 공백
- 통신 이상, 수집기 정지, 저장 경로 단절, 버퍼 넘침은 모두 "샘플이 없다"로 같게 드러난다

## 검토한 대안

- **구간 테이블 저장**: 조회는 빠르지만 늦게 도착한 샘플로 이미 닫은 구간을 고쳐야 하고, 원천이 둘이 된다
- **알람·heartbeat 기록으로 공백 판정**: 원인 구분은 되지만 원천이 여러 개라 샘플과 어긋날 수 있다
- **SQL 윈도 함수로 DB에서 계산**: 전송량은 적지만 판정 규칙이 CI 밖(DB)에 있게 된다
- **SQL은 상태 변화 지점만 추리고 C#이 합산**: 전송량이 줄지만 간격 규칙이 두 곳에 나뉜다

## 결과

- 조회 성능 목표는 두지 않고, 테스트 단계에서 측정값과 데이터 규모를 기록한다
- 기간이 길수록 DB에서 읽는 샘플이 많아진다(기본 설정에서 13일이면 설비당 약 112만 건, 계산값)
- **개선안**(조회가 느릴 때): 먼저 SQL이 상태 변화 지점·공백 경계만 추려 반환하는 방식을, 규모가 더 커지면 구간 테이블 저장을 검토한다
- 공백의 원인별 분류는 제공하지 않는다
- T를 바꾸면 과거 데이터의 공백 계산도 바뀐다
