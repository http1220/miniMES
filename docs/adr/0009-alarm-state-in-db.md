# 0009. 알람 상태의 진실은 DB

- 상태: 채택
- 날짜: 2026-09-30

## 맥락

- 알람은 수집기가 판정하지만, 수집기는 재시작하면 메모리의 알람 상태를 잃는다. 그러면 같은 원인의 알람이 중복 생성되거나 해제가 누락된다
- "저장됨" 응답이 유실되면 같은 알람 이벤트 묶음이 재전송된다. 한 묶음에 발생 → 해제 → 발생이 있으면 상태 규칙만으로는 잘못된 알람을 닫을 수 있다
- 두 사람이 같은 알람을 동시에 확인하거나, 같은 고장 기록을 동시에 전환할 수 있다

## 결정

- **설비 + 원인당 활성 알람은 최대 1건**을 DB 제약(필터된 고유 인덱스)으로 보장한다
- 수집기는 시작 후 설비·원인별 첫 판정이 나오면 **현재 상태를 한 번 보고**하고, Server가 활성 알람과 대조해 유지·해제·신규를 정한다
- 알람 이벤트는 **이벤트 로그 테이블**(키: 실행 ID + 이벤트 순번)에 기록하고, 이벤트 삽입과 알람 상태 반영을 **한 트랜잭션**으로 처리한다. 키가 겹치면 건너뛴다
- 알람 확인과 고장 상태 전환은 **"기대한 상태일 때만 갱신"하는 조건부 UPDATE**로 한 명만 성공시킨다

## 검토한 대안

| 대안 | 버린 이유 |
|---|---|
| 시작 시 활성 알람 목록 복원 | Server 없이 시작하면 복원할 수 없다 |
| 재시작 시 이전 알람 일괄 종료 | 지속 중인 원인에 알람이 다시 생겨 고장 기록이 쪼개진다 |
| 상태 기반 규칙만으로 중복 처리 | 재전송된 깜빡임 묶음에서 잘못된 알람을 닫는다 |
| 낙관적 동시성(rowversion) | "비어 있을 때만" 같은 단일 조건에는 과하다 |
| Server 메모리 잠금 | Server가 재시작하거나 여러 개면 보장이 깨진다 |

이 동시성 문제는 티켓 좌석 선점과 같은 종류다. 경쟁 규모가 커지면 앞단에 대기열이나 분산 락을 더할 수 있지만, 최종 보장은 DB에 둔다.

## 결과

- 알람의 현재 상태(알람)와 경위(이벤트 로그)가 분리돼, 알람이 왜 그렇게 됐는지 추적할 수 있다
- 조치 중 텍스트 필드를 동시에 편집하면 마지막 저장이 이긴다. 필요성은 상세 설계에서 다시 확인한다
