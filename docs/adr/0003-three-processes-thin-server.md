# 0003. 프로세스 3분리와 얇은 Server

- 상태: 채택
- 날짜: 2026-09-30

## 맥락

- 수집기가 죽었을 때 그 사실을 화면에 알려야 한다. 알릴 주체가 수집기 자신이면 성립하지 않는다
- 수집기·화면·DB는 서로 다른 PC, 서로 다른 LAN에 있을 수 있다
- 처음에는 수집기와 화면이 DB에 직접 붙는 2분리 구조를 택했으나, 그러면 화면 PC까지 DB 접속 정보를 갖게 된다

## 결정

```
수집기(콘솔) --HTTPS--> Server(콘솔) --> SQL Server
화면(WinForms) --HTTPS--> Server
```

- **DB에 접근하는 것은 Server뿐**이다
- Server의 역할은 셋으로 한정한다(얇은 Server)
  1. DB 접근 대행(쓰기·읽기)
  2. 시각 원천(ADR 0005)
  3. 상태 중계(수집기 heartbeat, DB 연결 상태를 화면에 전달)
- 권한 확인, 계산(지표 계산은 공용 Core 라이브러리 호출), 장비 명령 중계는 하지 않는다

## 검토한 대안

| 대안 | 버린 이유 |
|---|---|
| 단일 프로세스 | 수집기 사망을 감지할 수 없다 |
| 2분리, DB로만 연결 | 가장 단순하지만 DB 접속 정보가 여러 PC에 흩어진다 |
| 2분리 + 직접 통신 | 실패 경로가 늘고 DB 접속 정보 문제는 그대로다 |
| 완전한 Server(권한·계산·명령) | 구현 범위가 커져 실패 처리 증명에 쓸 시간이 줄어든다 |

참고한 구조: 오픈소스 SCADA인 Rapid SCADA는 장비 통신(Communicator), 데이터 보관(Server), 화면(Webstation)을 별도 애플리케이션으로 나눈다.

## 결과

- DB 접속 정보와 DB 쓰기 주체가 Server 한 곳으로 모인다
- 실패 지점이 하나 늘어난다(Server). 화면은 "Server 연결 끊김", "DB 연결 끊김", "수집기 정지"를 구분해 보여야 한다
- 프로세스 간 통신 방식은 ADR 0007
